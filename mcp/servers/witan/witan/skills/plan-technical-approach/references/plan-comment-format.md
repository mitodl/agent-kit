# Plan comment format

The shape of the plan comment created by
[`plan-technical-approach`](../SKILL.md) and regenerated by
[`implement-plan`](../../implement-plan/SKILL.md), and the marker contract that
lets it be updated in place instead of re-posted.

**The comment carries state and links. The record carries reasoning.**

That split is the whole format. Everything a reader needs to act on — which
chunk is live, which PR is open, what is blocking — is *derived* from the work
graph, so the comment is **rendered by
[`scripts/upsert-plan-comment.sh --render`](../scripts/upsert-plan-comment.sh)
rather than written**. Everything else — why this approach, what was traded
away, what was rejected — lives in the spec or the ADR, next to the code, where
it is reviewed in a pull request and where a future reader will actually look.

| Section | Spec or ADR route | Fast path (no record exists) |
|---|---|---|
| Approach, one line | the spec header / the ADR's `## Decision` | in the comment |
| Chunk rows, PR state, blockers | **rendered from the graph** | "Single PR, ~N lines" |
| Tradeoffs, Not chosen, Strongest argument against | the ADR | in the comment — it is the only record |
| How the plan moved | [the deviation log](deviation-log.md) | n/a |

**Why generated.** A derived artifact composed by hand drifts; one a script
renders from authoritative sources cannot. It also bounds the comment by
construction — no length budget to enforce — and it is what makes
regenerate-and-overwrite safe, because nothing in a rendered body was authored
by a session that could lose work to it.

Measured, on the first real use
([mitodl/hq#14080](https://github.com/mitodl/hq/issues/14080)): the
hand-written comment reached **18,344 characters across 12 edits**, of which
8,398 were an inline revision log and 2,690 restated an RFC that already said
it. The rendered equivalent is **under 1,000**.

## The marker contract

The comment opens with a marker line and closes with a digest line:

```text
<!-- ol-plan:v1 -->
...plan body...
<!-- ol-plan:sha:<sha256 of the canonical plan text> -->
```

**Both are written by `scripts/upsert-plan-comment.sh`, not by hand.** It
strips any markers in the body it is given before adding its own, so a body
that was round-tripped through a read cannot end up with two.

The marker is how the next run finds this comment instead of posting a second
one. The digest is how a session discovers it is about to overwrite an edit it
never saw.

**The digest is computed, not read.** It covers the *canonical plan text* — the
body with marker lines removed, CRs stripped, and leading and trailing blank
lines trimmed — so both sides can derive the same number: the writer from the
draft it is about to post, the reader from the body it just fetched. The digest
line itself is a human-readable fingerprint; **nothing verifies against it.**
That matters because an edit made in the GitHub UI rewrites the prose and
leaves the footer alone, so a check that trusted the footer would see an
unchanged digest and overwrite the edit.

**`--expect-sha` is not an atomic check-and-write.** GitHub's PATCH ignores
`If-Match`, so there is no compare-and-swap available. It detects an edit made
*before* the lookup; a write landing between that lookup and the PATCH still
wins silently. It guards against a stale draft, not against a race.

A comment retired by `--on-duplicate oldest|newest` carries
`<!-- ol-plan:v1:retired -->` instead. That marker is deliberately **not** a
prefix of the live one, so neither lookup selects it — minimizing alone left
the duplicate in the REST API that both lookups read, which is how a recovery
run used to leave the issue as wedged as it found it.

**The strip-HTML-comments rule does not apply here.**
`create-ol-github-issue`
says to strip `<!-- ... -->` from a finished issue **body**, where those
comments are leftover template instructions. This is a **comment**, and these
two markers are load-bearing: strip them and the next update silently posts a
duplicate instead of editing.

## Writing rules

These govern the text a human still writes — the `--note` line, a fast-path
body, and any separate comment. They do not apply to rendered output, which the
script already shapes. They are inherited, not local inventions:

- **Never hard-wrap.** Each paragraph and each bullet is one long line; GitHub
  wraps it for the reader. GitHub's comment renderer turns a single newline
  inside a paragraph into a line break, so an 80-column wrap that looks tidy in
  an editor renders as a column of ragged half-lines. Newlines belong between
  blocks, between list items, and inside code fences. See
  `configs/agent-communication-style.md`.
- **Self-contained.** The comment is public on a public repo and is read by
  people with no access to the machine that wrote it. No local paths, no
  internal hostnames, no secrets, no "see the output above". Reference code and
  issues by full GitHub URL.
- **Dates come from `date -u +%Y-%m-%d`,** never from memory. An agent's idea
  of today's date is routinely wrong, and a wrong date in a log someone reads
  in six months is worse than no date.
- **Voice.** Write as the engineer explaining the decision to a teammate. No
  throat-clearing, no inflated adjectives, no closing summary restating the
  body.

## What the renderer produces

`--render` reads the epic's chunk tasks, each chunk's linked pull request, and
the blockers recorded in the graph, and emits:

```markdown
**Plan:** <spec URL> · **Decisions:** <ADR links>
**Blocked on:** <the blockers actually holding a chunk>

| # | Chunk | PR | State |
|---|-------|----|-------|
| 1 | Static headers | [#4165](…) | merged |
| 2 | Cache-Control scoping | [#4183](…) | open, review required, checks failing |
| 3 | CSP report-only | — | blocked on tk-decide-d6 |

**Note:** <the one authored line, or omitted>
```

Every column comes from somewhere that is already authoritative, which is why
none of it is passed in:

| Column | Source |
|---|---|
| `#` | the chunk tasks' creation order — the order planning created them in |
| Chunk | the task title |
| PR | the task's `external_uri` |
| State | the PR's live state, else the task's status and its blockers |

**`--note` is the only free text, and it is capped at 280 characters.** It
exists for judgment the graph cannot imply — *"the bottleneck is review, not
work: #4157 has never had a non-bot review"* — and the cap is the point:
anything longer is reasoning, and reasoning belongs in the spec. The script
refuses past it rather than truncating.

**Two states that must never be confused with "no PR yet".** A chunk whose
lookup was disabled renders `PR state not fetched`; one whose lookup failed
renders `PR state unavailable`. A blank cell there would read as *nothing
opened yet*, which is the one misreading that gets work redone while it is
already in review.

**Zero chunk tasks is an error, not an empty table.** The script exits rather
than posting, because a comment claiming the work has no chunks would overwrite
a correct one with that claim.

## Template — fast path only

A change scoping classified as **trivial** has no epic, no chunk tasks and no
ADR, so there is nothing to render. It gets a short written body via
`--body-file`:

```markdown
## Plan

**Approach:** <one line naming the mechanism>

<One paragraph: what this does and why it won. Name the criterion that decided it.>

**Phases**

- [ ] <Phase 1> — done when <verifiable condition>

**Delivery**

Single PR, ~N lines.

**Status:** <current phase, or blocked on what>
```

Omit a section that has nothing in it. An empty **Tradeoffs** table is a
legitimate outcome — it means nothing was given up — and is more honest than a
row invented to fill it.

## Linking the ADRs

When decisions were recorded, name them under the approach. One line each, with
the title — a bare number tells a reader nothing.

```markdown
**Decisions:** [ADR-0014 — APISIX leaves bearer tokens to the applications](https://github.com/mitodl/ol-infrastructure/blob/main/docs/adr/0014-apisix-leaves-bearer-tokens.md)
```

Link by **full GitHub URL**, not a repo-relative path: the comment may sit on a
tracker issue in a different repo, where a relative path resolves to nothing.
Until the first PR merges those links 404, which is expected — ADRs land with
the first implementation PR. Say so in the comment if the work will sit
unmerged for a while.

A decision that changes during implementation is recorded as a dated addendum
on its ADR, and the change itself as one entry in
[the deviation log](deviation-log.md). Neither is noted here: the comment shows
the state that resulted, and the records carry why it moved.

Work with no ADRs — the fast path, or work whose choices were all obvious —
simply omits this line.

## Worked example — spec or ADR route (rendered)

Nothing below was typed except the `--note`. The command:

```bash
bash "$PTA/upsert-plan-comment.sh" --repo mitodl/mit-learn --issue 4120 \
  --render --epic tk-retry-consolidation-epic \
  --spec https://github.com/mitodl/mit-learn/blob/main/docs/plans/retry-consolidation-spec.md \
  --decisions "[ADR-0014 — retry policy belongs to the shared client wrapper](https://github.com/mitodl/mit-learn/blob/main/docs/adr/0014-retry-policy-in-client-wrapper.md)" \
  --note "Chunk 3 waits on chunk 2 reaching production, not merging: the old copy is the rollback target."
```

and what it posts:

```markdown
**Plan:** https://github.com/mitodl/mit-learn/blob/main/docs/plans/retry-consolidation-spec.md · **Decisions:** [ADR-0014 — retry policy belongs to the shared client wrapper](https://github.com/mitodl/mit-learn/blob/main/docs/adr/0014-retry-policy-in-client-wrapper.md)

| # | Chunk | PR | State |
|---|-------|----|-------|
| 1 | Retry policy in the client wrapper | [#4821](https://github.com/mitodl/mit-learn/pull/4821) | merged |
| 2 | Migrate the scheduler path | [#4834](https://github.com/mitodl/mit-learn/pull/4834) | open, approved |
| 3 | Delete the second copy | — | not started |

**Note:** Chunk 3 waits on chunk 2 reaching production, not merging: the old copy is the rollback target.
```

Note what is **absent and must stay absent**: no approach paragraph, no phase
checklist, no tradeoff ledger, no "not chosen" list, no strongest-argument
line, no revision log. Every one of those is in the spec or ADR-0014, both
linked above and both reviewed in a pull request. A second copy here would
drift, and the issue copy is always the one that goes stale.

The split axis, the estimated sizes and the paths each chunk touches are **on
the chunk tasks**, not here — `implement-plan` reads `Touches` from the task to
match it against each ADR's `applies_to` before the chunk's first edit.

## Worked example — sole candidate

All three examples below are **fast-path bodies**, posted with `--body-file`.
Work with chunk tasks is rendered instead; these are the case where there is
no epic to render from and no ADR holding the reasoning, so the comment is the
only record and carries it.

When planning found no genuine alternative, the comment must not look like the
output of a comparison. Drop **Not chosen**, keep the rest, and say so in one
line:

```markdown
## Plan

**Approach:** Add the missing `None` guard in `parse_window`.

No alternative mechanism found — the function has one caller, the input that crashes it is well defined, and every other shape of fix reduces to this same guard in a different place. Scored for its tradeoffs rather than ranked.

**Phases**

- [ ] Guard and regression test — done when the crashing input from the issue is covered and the suite is green

**Delivery**

Single PR, ~30 lines.

**Tradeoffs**

_None._ The guard is local to one function and reverts cleanly.

**Strongest argument against this plan:** it treats the symptom; the `None` arrives from an upstream parser that arguably should not emit it. Filed as a follow-up rather than widened into this fix.

**Status:** Phase 1 in progress.
```

## Worked example — trivial change (fast path)

A change that scoping classified as trivial skips the alternatives, the ledger
and any ADR entirely. The comment is four lines, and padding it out would add
nothing a reader wants.

```markdown
## Plan

**Approach:** Bump the empty-state copy to match the Figma, in `SavedSearchEmpty.tsx`.

Fast path — one obvious change, one component, no shared contract, reverts cleanly.

**Phases**

- [ ] Copy updated — done when the string matches the Figma and the snapshot test is regenerated

**Delivery**

Single PR, ~15 lines.

**Status:** In progress.
```

Note what is absent and should stay absent: no **Tradeoffs** table with a row
invented to fill it, no **Not chosen** section listing approaches nobody
considered, no **Strongest argument against** for a copy change. A reader
scanning this issue in six months gets what they need in one screen.

## Worked example — accepted workaround

The case the **Follow-up** column exists for. Note that the row is not a
complete record on its own: it points at an issue that carries the detail, and
the code carries a comment pointing at the same issue.

```markdown
## Plan

**Approach:** Cap the export at 10,000 rows and return a truncation notice.

The timeout is caused by building the whole export in memory before streaming it, and the real fix is a cursor-paginated streaming export — roughly a week, touching the serializer, the task runner and the download UI. The quarter-end reporting window opens Monday and the current failure blocks it entirely. Capping is a day, unblocks the window, and does not foreclose the streaming fix. Taken as a deliberate workaround, not as the design.

**Phases**

- [ ] Cap and truncation notice — done when an export over the cap returns the first 10,000 rows plus a visible notice, and the timeout no longer reproduces

**Delivery**

Single PR, ~120 lines.

**Tradeoffs**

| Giving up | To get | Revisit when | Decided by | Follow-up |
|---|---|---|---|---|
| Complete exports for the 4% of accounts over 10,000 rows, who now silently get partial data unless they read the notice | A working export before the quarter-end window opens Monday | Any account hits the cap twice in a month, or the reporting window closes — whichever is first | @rhysyngsun | mitodl/mit-learn#5120 |

**Strongest argument against this plan:** a truncation notice is easy to miss, so the failure mode changes from an obvious timeout to silently incomplete data — which is worse for anyone who does not read it. Accepted because the alternative is no export at all this quarter, and the follow-up is scheduled rather than aspirational.

**Status:** Phase 1 in progress.
```

The follow-up issue carries what this row cannot: why streaming was deferred,
what the real fix involves, and — once the workaround merges — the PR URL whose
diff has to be undone. The code gets `# Capped export: see mitodl/mit-learn#5120`
at the cap, which is how someone reading the serializer in six months finds any
of this.

## What gets a new comment

**An edit emails nobody. A new comment emails every subscriber.** That
asymmetry is invisible from inside an agent — both are one `gh` call — so it
has to be stated. On
[mitodl/hq#14080](https://github.com/mitodl/hq/issues/14080) four separate
comments were posted that no skill asked for, totalling ~14 KB, each one a
notification to everyone watching.

**Default: regenerate the sticky comment.** Every routine state change — a
phase done, a PR opened, a chunk merged, work blocked — is `--render` again.

**A new comment is for exactly two things:**

- A **question that needs a human who is not already in this thread**, and that
  the work cannot proceed without.
- A **terminal outcome**: shipped, abandoned, or blocked with no path forward.

**Never post a new comment for:**

| Not this | Because |
|---|---|
| An answer arriving | The spec's `Dn.` changes state and the rendered `Blocked on:` line clears. That *is* the announcement |
| Scoping findings, corrections, grounding notes | They belong in the issue body's acceptance criteria, or in the spec |
| Progress, phase completions, "now starting chunk 3" | The rendered table already says it, without the email |
| A revision to the plan | [The deviation log](deviation-log.md), in the PR that makes the change |

**One comment batches every open question**, addressed to the owners who can
answer them. Not one comment per question — and no follow-up comment when each
is answered.

**1,500 characters, hard, on any new comment.** Past that it is a document, not
a comment: put it in the repo and link to it. A reader scanning the issue in
six months should get what they need from one screen plus the links.
